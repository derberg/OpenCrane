# MCP Server Auth: Declarative Authentication & Scope-Based Content Authorization

**Status:** Design approved, pending implementation plan
**Date:** 2026-07-01

## Problem

The MCP server generated by OpenCrane exposes documentation search over HTTP with
**no access control**. Two distinct needs exist:

1. **A coarse access gate** — require credentials to talk to the server at all
   (HTTP Basic auth), configured declaratively.
2. **Fine-grained content authorization** — an OAuth resource-server model where a
   caller's token scopes determine *which sources* they may retrieve from the
   vector DB.

Both must be enabled by a maintainer through `config.yaml` + environment
variables only — **no Python required for the common cases**. The generated MCP
server (e.g. the `ai-docs` project) is served over HTTP via Docker; a maintainer
should turn on auth by editing config and passing secrets as env vars.

## Goals

- Native, declarative **HTTP Basic auth** gate (no extra dependency).
- Native, declarative **OAuth 2.0 / OIDC resource-server** validation of bearer
  JWTs (optional dependency), reading scopes from the token.
- Declarative **scope → sources** mapping that constrains search results.
- **Fail-closed** on misconfiguration; secrets never live in `config.yaml`.
- Escape-hatch **extension points** (`authenticator`, `access_policy` on
  `OpenCraneConfig`) for non-standard IdPs or custom policies.
- 100% test coverage, no regression to the existing unauthenticated path.

## Non-Goals

- OpenCrane acting as a full **authorization server** (issuing tokens, login UI,
  client registration). It is strictly a **resource server**.
- Auth on the **stdio** transport — stdio is local/single-user and always runs in
  `none` mode.
- Per-chunk or per-topic tagging. Authorization gates at the **source** level only
  (`source_name`), which is already an indexed, filterable field. No schema change
  or reindex.
- Multi-user Basic auth or password hashing in `config.yaml` (single credential
  via env only; can be added later additively).

## Architecture: two independent layers

Authentication (*who are you / may you connect*) and authorization (*what may you
see*) are separate concerns and separate config. Conflating them is the usual
source of unauditable auth code.

```
HTTP request
   │
   ▼
[Layer 1: Authentication]  ── HTTP gate (Starlette), runs before tool dispatch
   │  none | basic | oauth | custom
   │  → produces a Principal (identity + claims/scopes)   or  401
   ▼
[MCP tool dispatch]  ── request→Principal context threaded down to the tool layer
   │
   ▼
[Layer 2: Authorization]  ── access_policy(principal, requested_sources)
   │  scope_sources mapping | custom | allow-all (default)
   │  → allowed source_names   or  deny (403)
   ▼
[Enforcement]  ── AND allowed source_names into Milvus AND BM25 search filters,
                  intersected with any client-supplied source_names (narrow-only)
```

### Layer 1 — Authentication (the HTTP gate)

Selected by `auth.type` in `config.yaml`. Runs as Starlette middleware on the HTTP
transport, before any MCP tool is dispatched. Its output is a `Principal`.

| `auth.type` | Behavior | Dependency |
|-------------|----------|------------|
| `none` (default) | No gate. Anonymous `Principal`. Current behavior, unchanged. Always the effective mode for stdio. | none |
| `basic` | HTTP Basic. Credentials from **env only**. Constant-time compare. Missing/invalid → `401` + `WWW-Authenticate: Basic`. | none |
| `oauth` | Validates a bearer JWT as an OAuth 2.0 / OIDC resource server: JWKS auto-discovered from `issuer`, verifies signature, `audience`, expiry. Scopes read from the configured claim. Missing/invalid → `401` + `WWW-Authenticate: Bearer`. | `opencrane[auth]` extra |
| `custom` | Uses `OpenCraneConfig.authenticator`, a consumer-supplied object/callable `authenticate(request) -> Principal` (raises `Unauthorized` to reject). Escape hatch for non-standard IdPs. | consumer-defined |

**Basic auth credentials** (`basic`):
- `OPENCRANE_BASIC_AUTH_USER` and `OPENCRANE_BASIC_AUTH_PASS` env vars.
- Compared with `secrets.compare_digest` (constant time).
- **Fail-closed:** if `auth.type: basic` but either env var is unset/empty, the
  server refuses to start (clear error), rather than booting open.

**OAuth config** (`oauth`) — all declarative in `config.yaml`:
```yaml
auth:
  type: oauth
  oidc:
    issuer: https://login.example.com/realms/docs   # JWKS discovered from issuer
    audience: opencrane-docs
    scope_claim: scope        # default "scope" (space-delimited); IdPs vary (scp, permissions, …)
```

### Layer 2 — Authorization (content scoping)

Runs at the tool layer after authentication, given the `Principal`. Produces the
allowlist of `source_name`s the caller may retrieve, or a hard deny.

**Built-in declarative policy** — driven by `config.yaml`:
```yaml
auth:
  type: oauth
  scope_sources:                 # scope -> which configured sources it unlocks
    "docs:public":   [cennso-glossary]
    "docs:cennso":   [extension-cennso, extension-cennso-db, cennso-glossary]
    "docs:internal": [cgw, tsr, tposs]
  default_sources: []            # sources an authenticated token with NO matching scope may see
```

Resolution semantics:
- A caller's allowed set = **union** of `scope_sources[s]` for every scope `s` the
  `Principal` carries; if none match, `default_sources`.
- The allowed set is **intersected** with any `source_names` the client passed to
  the search tool. A client may **narrow** within what it is permitted but can
  never **widen** past it.
- Empty allowed set → empty results (not an error). Explicit hard-deny path (e.g.
  a future policy returning `Deny`) → `403`.
- All source names in `scope_sources`/`default_sources` are validated against the
  known `config.yaml` source keys at load time; unknown keys → startup error.

**Default policy** when `scope_sources` is absent = **allow all** sources. So
`type: basic` (gate only, no `scope_sources`) grants every authenticated caller
all sources.

**Custom policy** — escape hatch: `OpenCraneConfig.access_policy`, a
consumer-supplied `authorize(principal, requested_sources) -> allowed | Deny`,
overrides the built-in declarative policy.

## Core plumbing (the enabling change no consumer can do externally)

Today the MCP tool handlers receive only the tool `arguments` dict — the incoming
HTTP request (and its `Authorization` header) is never propagated to
`call_tool` / `_search_documentation_impl`. Two core changes:

1. **Request/principal context propagation.** The HTTP authentication middleware
   resolves a `Principal` and stores it in a `contextvar`; the tool layer reads it.
   For stdio and `type: none`, the `Principal` is anonymous. This keeps the MCP
   tool signatures unchanged.
2. **Enforcement at search time.** In `_search_documentation_impl`, resolve
   `allowed = access_policy.authorize(principal, args.source_names)`, then pass
   `allowed` as the `source_names` filter into **both** `MilvusService.search` and
   `KeywordSearchService.search`. Both backends already accept a `source_names`
   filter, so no new filtering machinery is needed — only that the allowlist is
   applied server-side and cannot be bypassed by the client.

## New/changed components

| Component | Location (indicative) | Responsibility |
|-----------|----------------------|----------------|
| `Principal`, `Deny` types | `opencrane/mcp/auth/` (new) | Identity + claims/scopes; hard-deny signal. |
| `Authenticator` protocol + built-ins (`NoneAuth`, `BasicAuth`, `OAuthAuthenticator`) | `opencrane/mcp/auth/` | Turn a request into a `Principal` or reject. |
| `AccessPolicy` protocol + built-ins (`AllowAll`, `ScopeSourcesPolicy`) | `opencrane/mcp/auth/` | Turn `(principal, requested_sources)` into an allowlist or `Deny`. |
| Auth config parsing | `opencrane/shared/config.py` / `config.yaml` schema | Parse+validate the `auth:` block; fail-closed. |
| HTTP middleware wiring | `opencrane/mcp/http_server.py` | Install the authenticator; set the `Principal` contextvar; map failures to 401/403. |
| Context + enforcement | `opencrane/mcp/server.py` | Read `Principal`; call `access_policy`; constrain `source_names` in both search backends. |
| `OpenCraneConfig` hooks | `opencrane/config.py` | Optional `authenticator` and `access_policy` attributes (default: built-ins driven by config). |
| `[auth]` optional extra | `pyproject.toml` | JWT/JWKS validation dependency (e.g. PyJWT with crypto), imported lazily only for `type: oauth`. |

## Error handling & security

- **Fail-closed:** any auth misconfiguration (e.g. `basic` with no creds, `oauth`
  with no `issuer`, `scope_sources` referencing an unknown source) is a startup
  error, never a silent open server.
- **Constant-time** credential comparison for Basic auth.
- **Server-side enforcement only:** the existing `source_names` tool parameter
  stays a *narrowing convenience*; it is never a way around policy.
- **Least privilege by default in gated modes:** an authenticated token with no
  matching scope sees only `default_sources` (default `[]` → nothing).
- **Secrets via env only**, never `config.yaml` (which is typically committed).
- **`serve` logs the active auth mode** at startup (not the secrets).
- Lazy import of the JWT dependency: absent `opencrane[auth]` + `type: oauth`
  yields a clear "install the auth extra" error.

## Testing (100% coverage gate)

Unit tests, all with fakes (no real IdP, no real JWT dep required in core tests):

- **`none`/anonymous:** existing unauthenticated path unchanged; anonymous
  `Principal` reaches the tool layer; allow-all applies.
- **Basic:** valid creds → `200`; missing/invalid → `401` + `WWW-Authenticate`;
  missing env creds → **startup fails closed**; comparison is constant-time.
- **OAuth (mocked validator):** valid token → scopes on `Principal`; bad
  signature/audience/expiry → `401`; scope claim parsing across formats.
- **Context propagation:** the resolved `Principal` is readable in the tool layer.
- **`scope_sources` policy:** union across scopes; `default_sources` fallback;
  unknown-source-key → startup error; empty allowlist → empty results.
- **Enforcement:** allowlist AND-ed into **both** Milvus and BM25 filters;
  client-supplied `source_names` intersected (narrow OK, widen blocked); hard
  `Deny` → `403`.
- **Custom hooks:** `authenticator` and `access_policy` overrides exercised via
  fakes.

## Maintainer experience (target: `ai-docs/.opencrane`)

**Basic auth — config + env, no Python:**
```yaml
# config.yaml
auth:
  type: basic
```
```yaml
# docker-compose.yml (env passed from host/secret store)
    environment:
      OPENCRANE_BASIC_AUTH_USER: ${OPENCRANE_BASIC_AUTH_USER:?set me}
      OPENCRANE_BASIC_AUTH_PASS: ${OPENCRANE_BASIC_AUTH_PASS:?set me}
```

**OAuth scope-gated content — config + env + the `[auth]` extra, no Python:**
```yaml
# config.yaml
auth:
  type: oauth
  oidc:
    issuer: https://login.example.com/realms/docs
    audience: opencrane-docs
    scope_claim: scope
  scope_sources:
    "docs:public":   [cennso-glossary]
    "docs:internal": [cgw, tsr, tposs]
  default_sources: [cennso-glossary]
```
Dockerfile installs `opencrane[auth]` instead of `opencrane`. A caller presenting
a token with only `docs:public` can retrieve only `cennso-glossary`; both the
semantic and keyword backends filter to it.

## Open questions / deferred

- Multi-user Basic auth + hashed creds in config — deferred (additive).
- A `[auth]` built-in that also supports opaque tokens + introspection endpoint
  (RFC 7662) rather than JWTs — deferred; `custom` authenticator covers it today.
- Rate limiting / audit logging of denied requests — out of scope.
